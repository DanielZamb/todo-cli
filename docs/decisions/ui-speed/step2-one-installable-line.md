## What the installed build does differently on the owner's machine

Nothing is migrated in the Task database: no schema change since candidate 10.
Beside the real database, the server creates at its start:
- `.todo-routing/` (mode 0700), holding the guard file
  `<device>-<inode>-<birth>.sqlite` (one server per database; held while the
  server runs) and `<hex of the database name>/endpoint.json`, the private
  record the CLI reads to find and prove the server (withdrawn when the server
  stops). Not created when the database file has more than one hard link.
- `diagnostic-recordings/` (mode 0700) with `recordings.db` and its `-wal` and
  `-shm`, the recordings store, opened by its worker at server start. It
  holds nothing until an app uploads recordings; neither app does yet.

Every CLI writing command then looks for that record (at most 50 ms) and sends
one nudge (at most 50 ms). Today and Overdue follow the server's own zone
instead of the UTC date. The Catalog seat's list of visible changes applies:
Today counts a Task once, Electron's All badge counts open Tasks only, the name
order, undated Tasks last inside a priority; the CLI's `due:` label stays an
instant's UTC date.

Reinstalling candidate 10 undoes the behaviour but not the files: candidate 10
never reads `.todo-routing/` or `diagnostic-recordings/`, so they stay beside
the database, harmless, until removed by hand. The Task database itself is
unchanged in schema and readable by candidate 10.
